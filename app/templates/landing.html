WHAT ARRNEXUS IS

The intelligence layer above your stack.

A modern media stack is powerful, but each application normally understands only its own part of the workflow. ArrNexus is the missing layer that can view, reason about and automate across those boundaries.

THE PROBLEM

Excellent tools. Separate worlds.

Radarr knows movies. Sonarr knows TV. Lidarr knows music. Prowlarr knows indexers. Seerr knows requests. Jellyfin consumes the finished library. DUMB, NzbDAV/InfiniDysk and Decypharr handle virtualised acquisition. DMM is brilliant at finding cached Debrid content. ArrNexus gives those systems one shared operational view.

Why it was created

ArrNexus began as a DMM → Arr helper: identify media already present through Debrid Media Manager, match it to the correct Arr item, route it into the existing virtual/symlink library and let the Arr applications and Jellyfin remain the managed-library source of truth.

What it became

The project grew into a wider media operations layer: discovery, acquisition strategy, TV pack planning, music browsing, Prowlarr control, language validation, provider management, self-healing, diagnostics, telemetry and readiness checks.

REFERENCE ARCHITECTURE

ArrNexus controls the flow — it does not become the downloader.

You do not need every component shown here. This is the reference environment the project was developed around.

Users / Seerr→Radarr / Sonarr / Lidarr→Prowlarr / acquisition decision→Usenet or Debrid backend→Virtual / linked library→Jellyfin / Plex / Emby
ArrNexus sits across that chain: it understands the Arr applications, DMM/Debrid sources, provider capabilities, virtual mounts, library state and operational telemetry while leaving ownership of downloads and managed libraries with the specialist tools.

INSTALLATION

Download, validate, then build with Docker.

v9.4 keeps the host-side Python validator explicit and adds deployment patterns for source builds, Portainer Git stacks and future prebuilt GitHub Container Registry images. Debian's system Python may not have FastAPI installed, so the recommended validation path uses a local virtual environment rather than polluting system packages.

1 · Fresh ZIP installation

Install the small host tools, extract ArrNexus and validate the source package before building the container.

sudo apt update sudo apt install -y unzip python3-venv unzip arrnexus-v{{ version }}.zip cd arrnexus-v{{ version }} python3 -m venv .venv source .venv/bin/activate python -m pip install --upgrade pip python -m pip install -r requirements.txt python validate.py deactivate docker compose config docker compose up -d --build

2 · Confirm the service

The default Compose mapping exposes ArrNexus on host port 8484 and persists application state in ./data.

docker compose ps docker compose logs --tail=200 arrnexus curl -fsS http://127.0.0.1:8484/api/health echo

Then open http://<ARRNEXUS_HOST>:8484 and complete the guided setup.

3 · Upgrade an existing ZIP deployment

Build each release beside the previous one. Stop the old container, extract the new source, copy only persistent data, validate, then start the new build.

cd /path/to/old-arrnexus docker compose down cd /path/to/releases unzip arrnexus-v{{ version }}.zip mkdir -p arrnexus-v{{ version }}/data cp -a old-arrnexus/data/. arrnexus-v{{ version }}/data/ cd arrnexus-v{{ version }} python3 -m venv .venv source .venv/bin/activate python -m pip install --upgrade pip python -m pip install -r requirements.txt python validate.py deactivate docker compose config docker compose up -d --build

4 · Portainer Git stack

Create a Portainer stack from the public Git repository, use docker-compose.yml, keep ./data:/data persistent and rebuild when the Dockerfile or dependencies change. Normal configuration belongs in the UI/database rather than a large deployment .env.

Before major upgrades, back up the persistent data directory. Never replace or bulk-migrate library roots just because another deployment uses different paths.

5 · Git clone + Docker Compose source build

Once the public repository is on GitHub, CLI users can clone the source directly and let Compose build the same Dockerfile included in the ZIP release.

git clone https://github.com/<GITHUB_OWNER>/ArrNexus.git arrnexus cd arrnexus docker compose config docker compose up -d --build docker compose ps

For a source-level release validation first, create the Python virtualenv shown in step 1 and run python validate.py before the Docker build.

6 · Docker Compose using a published GitHub image

When the official ArrNexus image is published to GitHub Container Registry, users will be able to deploy without building locally. Replace <GITHUB_OWNER> with the real repository owner/release path.

services: arrnexus: image: ghcr.io/<GITHUB_OWNER>/arrnexus:latest container_name: arrnexus restart: unless-stopped pid: host cap_add: - SYS_PTRACE extra_hosts: - "host.docker.internal:host-gateway" ports: - "8484:8000" volumes: - ./data:/data
This image reference is a release template until the official GHCR package is published. Do not pull an unofficial image just because it uses the ArrNexus name.

7 · Portainer Web editor / Stack file

Once the GHCR image exists, paste the same Compose definition into Portainer → Stacks → Add stack → Web editor. This is the easiest image-pull deployment for users who do not want a Git checkout on the Docker host.

Stack name: arrnexus Image: ghcr.io/<GITHUB_OWNER>/arrnexus:latest Persistent volume: ./data:/data Published port: 8484:8000 PID mode: host Capability: SYS_PTRACE

After deployment, open http://<ARRNEXUS_HOST>:8484 and complete the first-run wizard. Configuration/API keys belong in ArrNexus persistent state, not the Portainer stack.

DOCKER NETWORKING

The URL must work from inside ArrNexus.

A service URL that works in your desktop browser may still be unreachable from the ArrNexus container.

Shared Docker network

http://radarr:7878 http://sonarr:8989 http://lidarr:8686 http://prowlarr:9696

Use the real Docker service names in your environment.

Do not blindly use localhost

Inside the ArrNexus container, localhost and 127.0.0.1 refer to ArrNexus itself. For services elsewhere, use a routable hostname, container DNS name or reverse-proxy URL.

FEATURE GUIDE

What the main ArrNexus areas actually do.

This section mirrors the project README so a new visitor can understand the product before they install it.

Dashboard · operations overview
High-level service health, library state, DMM backlog, downloads, recent activity, registered libraries and Stack Readiness. v9.3 retains a short-lived snapshot and background refresh so opening Dashboard does not have to rescan the whole stack.
Discover · cross-service discovery and acquisition
Combine local Arr/media-server context with metadata discovery, compare acquisition routes and use the selected Automatic / Debrid-first / Usenet-first / provider-specific strategy.
DMM / Debrid Inbox
Review media already present through DMM/Debrid, identify the owning movie/show, group duplicates, inspect Language Guard, select explicit routes and create managed library links without deleting the underlying source.
Quality Lab & TV pack planning
Explain release scores and compare full-series packs, season packs and episodes against Sonarr coverage. Use real season-number interactive searches rather than pretending a series ID is a show-wide search.
Music Hub
Separate provider-specific music discovery from global trend sources. Personal Spotify OAuth can expose saved tracks/albums, playlists, top tracks/artists and recently played items before handing acquisition to Lidarr/Prowlarr. v9.3 adds a dedicated Music API Settings page so SoundCloud/Jamendo/Last.fm/Spotify application credentials are no longer buried in general settings.
Providers & AIOStreams
Manage provider capabilities without assuming Real-Debrid. The AIOStreams Bridge performs GET → digest → masked preview → stale re-check → private backup → full PUT → verification, with rollback and secret-redacted search diagnostics.
Media servers · InfiniDysk / NzbDAV / Decypharr / DUMB
Attach Jellyfin, Plex, Emby or a custom external media-server endpoint; expose native InfiniDysk telemetry, strict protected connector checks, virtual-media awareness and the special DUMB Arr mount namespace used when useful media paths exist under /proc/<PID>/root/… rather than the host filesystem.
Problem Centre · Self-Healing · Maintenance
Turn broken links, missing media, upgrade candidates and operational faults into bounded work queues. Backups, sanitized diagnostics and undo operations focus on ArrNexus-created links rather than destructive source deletion.

DMM & VIRTUAL MEDIA

Source, virtual layer and managed library are different things.

ArrNexus was built specifically to reason about this distinction rather than assuming every library item is a normal copied file.

DMM / Debrid source→ArrNexus identity + policy→NzbDAV / Decypharr / DUMB virtual layer→Managed Arr library→Jellyfin / Plex / Emby
Language Guard rejection is intentionally non-destructive: a non-compliant source can remain in Debrid/DMM while ArrNexus asks the owning Arr application to find a replacement.
ACQUISITION STRATEGIES

Choose how ArrNexus should compare routes.

Automatic

Compare acceptable Usenet and Debrid candidates and choose the best route.

Debrid first → Usenet

Prefer Debrid/cached availability, then fall back to Usenet when required.

Usenet first → Debrid

Prefer the Usenet path, then use Debrid as fallback.

Focused strategies

Debrid only, Usenet only, fastest/cached, or best quality/score are available when the connected services support them.

DESIGNED FOR REAL LIBRARIES

Safety is part of the architecture.

Non-destructive by default

Language rejection and routing problems do not delete the original DMM/Debrid source.

Preview before risky changes

AIOStreams full-config writes use digest checks, masked previews, backups and rollback.

Secrets stay private

Credentials live in persistent state, are masked in UI/logs and are excluded from public release exports.

Performance visible

v9.3 retains route timing headers and logs requests that exceed 1.5 seconds so slow pages can be profiled instead of guessed at.

TROUBLESHOOTING

Quick checks before you start changing things.

Connector fails

  1. Test it in Connections.
  2. Confirm the URL is reachable from the ArrNexus container.
  3. Do not use localhost for another container.
  4. Verify the API key/token belongs to the correct service.
  5. Check Docker networks and DNS.
  6. Open Unified Logs for the real error.

ArrNexus fails to start

docker compose ps docker compose logs --tail=300 arrnexus

For a host-side source validation, use the Python virtualenv procedure in the Installation section above.
